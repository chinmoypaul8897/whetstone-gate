# QUESTIONS.md — every ambiguity hit, and every ruling made

**A ruling that exists only in a chat does not exist.** Rulings are recorded here **verbatim**,
before anything else is touched (`CLAUDE.md` hard rule 5), and a recorded ruling binds every later
session.

---

## The format

Every item is a numbered question. **Nothing is deleted; a question is closed by filling in its
ruling, not by removing it.**

```
### Q-NNN — <one-line title>
**Raised by:** <chunk> <BUILD|REVIEW|FIX> · **Date:** <ISO-8601> · **Status:** OPEN | RULED | WITHDRAWN
**Blocking:** <what cannot proceed until this is answered — or "nothing; unblocked work continued">
**Deviation class:** A (changes meaning, behaviour, or a reported number — STOP and ask) |
                     B (implementation choice within spec — do it, record it, judged at review) |
                     C (cosmetic — one line) | n/a
**Context:** <the exact text of the spec / process / prompt clauses that conflict or are silent,
quoted, with file and section>
**Options seen:**
  1. <option> — <consequence>
  2. <option> — <consequence>
**Default taken pending a ruling:** <what the session actually did, and why it is the reversible
choice> — or "none; work stopped on this item"

**RULING (architect, <ISO-8601>):** *<verbatim. Not paraphrased.>*
```

**Deviation classes are `CLAUDE.md` hard rule 2.** A **Class A** item may not be defaulted past — the
session stops that item, records it, and continues any unblocked work (hard rule 1). A session that
stops on a real ambiguity has succeeded.

## Concurrent pairs

`PROCESS.md` §1. Up to **two BUILD sessions** may be in flight at once, if and only if their SCOPE
FENCEs are disjoint and neither imports the other. **The architect records the pair here BEFORE
issuing either prompt.** **REVIEW sessions remain strictly serial**, and a chunk's review may not
begin before the architect has recomputed that chunk's build report and committed its
`ARCHITECT_CHECK`.

| Pair | Chunks | Fences (disjoint) | Recorded | Issued |
|---|---|---|---|---|
| P-01 | C0-FIX (`c9521aac`) + C1 BUILD (`20cd5b79`) | C0-FIX: `src/whetstone_gate/{check_roles,config,spec_constants}.py`, `tests/` · C1: `RAZORPAY_SEMANTICS.md`, `PROVENANCE.md` | 2026-08-31 | 2026-08-31 |

*(Before P-01: no concurrent pairs. C0 ran alone.)*

⚠️ **ARCHITECT RULING — the rule is EXTENDED, and that is recorded rather than assumed.**
`PROCESS.md` §1's concurrency rule names *"two **BUILD** sessions"*. **P-01 is one FIX and one
BUILD.** The rule's substance is that **the SCOPE FENCES ARE DISJOINT and NEITHER IMPORTS THE
OTHER**, and both hold here: C0-FIX owns three source modules and `tests/`; C1 owns two root
markdown documents and imports nothing. **The rule is therefore extended to cover a FIX+BUILD
pair.** It is written down here instead of being taken as obvious.

⚠️ **THE FENCES ARE DISJOINT IN SOURCE BUT NOT IN THE JOURNALS, AND THAT IS THE REAL HAZARD.**
Both sessions must append to `STATUS.md`, `PROGRESS.md` and — C0-FIX certainly, C1 possibly —
`INCIDENTS.md`. **File-writing is already this project's single largest defect source:** `INC-06`,
`INC-10` and `INC-12` are three occurrences of the same class in three different sessions.

**THE OPERATOR'S BOUND, recorded verbatim as it is carried in both prompts:** *"append only, never
rewrite another session's lines, re-verify your own bytes after any rebase"*, and **IF A PUSH IS
REJECTED TWICE FOR THE SAME SESSION, THAT SESSION STOPS AND WAITS** rather than grinding on a
rebase loop.

### Q-001 — the C0 build prompt carried no `SESSION-TOKEN`, and this session did not invent one
**Raised by:** C0 BUILD · **Date:** 2026-08-30 · **Status:** **RULED** (architect, 2026-08-31) —
*was OPEN from 2026-08-30 until the ruling below landed*
**Blocking:** nothing; unblocked work continued. But **every C0 commit is missing its `Session-Token`
trailer**, and `make check-roles` cannot verify C0's build/review separation until this is resolved.
**Deviation class:** A — it disables a stated process control.
**Context:**
- `PROCESS.md` §7: *"Every commit carries the trailer `Session-Token: <token>` (§7a)."*
- `PROCESS.md` §7a: *"Every build, review and fix prompt opens with `SESSION-TOKEN: <8 random hex>`,
  generated fresh by the architect, never reused, and recorded in `QUESTIONS.md` under
  `## Session tokens`… **`make check-roles`** (built in C0) fails if any chunk's build and review
  commits share a token, **if a token appears that was never issued**, or if a token is reused
  across roles."*
- `PROCESS.md` §10 template 1: the build prompt's first line is `SESSION-TOKEN: <8 hex>`.
- **The C0 build prompt as issued opens with `CHUNK C0 — REPOSITORY, TOOLCHAIN AND CANONICAL FILES.`
  and contains no `SESSION-TOKEN` line.** Its GIT section names atomic commits, the `(unreviewed)`
  marker, STATUS/PROGRESS/INCIDENTS updates and the push — and does not mention the trailer.

**Options seen:**
  1. **Generate a token in-session and use it.** — It would appear in the log as a token *that was
     never issued*, which is precisely one of the three conditions `check-roles` exists to catch.
     It would put a forged credential in the audit trail of a project whose thesis is that
     self-certified evidence is worthless.
  2. **Omit the trailer, record the gap, and let the architect issue C0's token retroactively.** —
     C0's commits are permanently untrailered (no history rewrite is permitted, `PROCESS.md` §7), so
     the gap is visible forever rather than papered over. `check-roles` must therefore tolerate a
     commit with no trailer while still failing on a *forged* or *reused* one.
  3. **Stop and refuse to commit until a token is issued.** — Would deliver nothing, and §7a's
     control is about build-vs-review separation, which no C0 commit can violate on its own.

**Default taken pending a ruling:** **option 2.** No trailer on any C0 commit; no token fabricated;
`## Session tokens` above left empty; `make check-roles` implemented to fail on an **unissued** or
**reused** token and to report an **untrailered** commit as a warning naming Q-001, not as a pass.
This is the reversible choice: issuing C0's token later and amending nothing costs nothing, whereas
an invented token in an immutable log cannot be withdrawn.

**RULING (architect, 2026-08-31):** *UPHELD. The default taken was correct and NO token is
issued for C0 retroactively. C0's commits stay permanently untrailered. History is never
rewritten, so the trailer cannot be added; and adding a row to `## Session tokens` for a token
that appears on no commit would place a credential in the issued table that was never carried -
the mirror image of the forgery E1 exists to catch. The gap is permanent, visible and explained,
and C19 publishes it as a stated limitation in the README's S7a paragraph rather than burying
it. The session was right to refuse to fabricate one; that refusal is the single clearest piece
of evidence in this repository that its own audit trail is not decorative.*

### Q-004 — `CONTEXT.md` §16's tree is ambiguous about whether the subpackages live inside `whetstone_gate/` or beside it
**Raised by:** C0 BUILD · **Date:** 2026-08-30 · **Status:** **RULED** (architect, 2026-08-31) —
*was OPEN from 2026-08-30 until the ruling below landed*
**Blocking:** nothing in C0 — the scope fence forbids creating any of these modules here.
**Blocking C2, C4, C7, C8, C9, C10, C11 the moment one of them is built.**
**Deviation class:** A — it decides every import path in the project, and rule 8's module-graph test
walks those paths.
**Context:** `CONTEXT.md` §16 draws:

```
├── src/
│   └── whetstone_gate/       # the installable package; `tasks.py` is the make-free entry point
│   ├── attacker/             # policy-blind LLM loop, sliding-window context
│   ├── benign_solver/        # policy-blind LLM loop that TRIES TO SUCCEED
│   ├── gates/                # arms 1, 2, 2S, 3, 4 — one file each. FIVE FILES.
…
```

**The drawing is self-inconsistent:** `└──` marks a last entry, yet eleven `├──` entries follow it at
the same indent. So the tree cannot be read literally, and the two readings differ in every import
path in the repository.

**Options seen:**
  1. **The subpackages are children of the package:** `src/whetstone_gate/gates/`,
     `src/whetstone_gate/scorer/`, … — Consistent with *"the installable package"*, with
     `python -m whetstone_gate.tasks` (the entry point named in `CONTEXT.md` §16 and §20), and with a
     standard src-layout. Makes `gates` and `scorer` importable as `whetstone_gate.gates` /
     `whetstone_gate.scorer`, which rule 8's **first-party** module-graph walk needs in order to have
     a first-party graph to walk at all.
  2. **The subpackages are siblings of the package under `src/`:** `src/gates/`, `src/scorer/`, … —
     Matches the ASCII art's literal indentation, and matches how `CONTEXT.md` §14 and `PROCESS.md`
     §4 rule 8 *name* them in prose (*"`scorer/` imports nothing from `gates/`"*,
     *"`gates/arm4_kernel.py`"*). But it leaves eleven top-level distribution packages with generic
     names (`world`, `runner`, `probe`, `scorer`, `gates`) outside the installable package, and

**RULING (architect, 2026-08-31):** *OPTION 1. THE SUBPACKAGES ARE CHILDREN OF THE PACKAGE.*
*Every one of the eleven lives under `src/whetstone_gate/`: `attacker/`, `benign_solver/`,
`gates/`, `world/`, `tau2/`, `agentdojo/`, `camel_comparator/`, `probe/`, `runner/`, `ledger/`,
`scorer/`. Import paths are `whetstone_gate.gates.arm4_kernel`, `whetstone_gate.scorer.replay`,
`whetstone_gate.world`, and so on. There is no top-level `gates`, `scorer`, `world` or `tau2`.*

*Three reasons, in the order that decides it.*

*(i) THE DECIDING FACT, VERIFIED AT SOURCE 2026-08-31 rather than reasoned from the tree:
`vendor/tau2-bench/pyproject.toml` declares `name = "tau2"` and `vendor/tau2-bench/src/` contains
`tau2/` and `experiments/`, so tau2-bench INSTALLS A TOP-LEVEL PACKAGE CALLED `tau2`.
`CONTEXT.md` S16 also places OUR adapter at `src/tau2/`, and our `pyproject.toml` carries
`[tool.setuptools.packages.find] where = ["src"]`. Under the sibling reading, `pip install -e .`
would publish a second top-level `tau2` in direct collision with the benchmark that S21.4 calls
undroppable and that this project's entire external-answer-key claim rests on. That is not a
style preference; it is an import collision with the project's spine.*

*(ii) The sibling reading publishes ELEVEN generic top-level distributions - `import world`,
`import gates`, `import scorer`, `import runner`, `import probe` - into the environment of every
reviewer who runs the install command the README will print. S16 calls
`src/whetstone_gate/` "the installable package" and S16 and S20 both name

*(iii) Hard rule 8's module-graph test needs a FIRST-PARTY graph to walk. Under this ruling every

decidable rather than a guess about which top-level names happen to be ours.*

*CONSEQUENCE, STATED BECAUSE IT IS NOT FREE AND MUST NOT BE MISSED: this ruling is exactly what
makes `check_roles.py`'s `shared = (gate_imports & scorer_imports) - {"whetstone_gate"}`
dangerous. Under the sibling reading the package root would never be a shared import string;

*The prose in `CLAUDE.md` hard rule 8 and `CONTEXT.md` S7 and S14 - "`scorer/` imports nothing
from `gates/`", "`gates/arm4_kernel.py`" - reads under this ruling as DIRECTORY NAMES RELATIVE TO
THE PACKAGE. No rule text changes. S16's tree is corrected in Task 4 so that it stops being
self-inconsistent.*

### Q-015 - `check_roles` D3 carries an unruled allow-list entry, and hard rule 8 says adding one is Class A
**Raised by:** C0 REVIEW (`52f5307b`) - **Date:** 2026-08-30 - **Status:** **RULED** (architect,
2026-08-31) - *was OPEN - **ARCHITECT ACTION REQUIRED** from 2026-08-30 until the ruling below
landed*
**Blocking:** nothing today (D1/D2/D3 report `n/a` — neither directory exists). **Blocks C8 and C9**,
whose done-when items assert the moat through this code.
**Deviation class:** **A**, and hard rule 8 names it as one explicitly.

**The rule, verbatim (`CLAUDE.md` hard rule 8):**
> The test is a module-graph walk over both packages' transitive first-party imports, failing on any
> shared first-party module **outside a short, explicit allow-list of pure value types (enums, the
> harm-record dataclass, the paise integer wrapper) that carry no predicate logic**. **Adding to that
> allow-list is a Class A deviation** requiring an architect ruling in `QUESTIONS.md`.

**What the code does.** `check_roles.py:_walk_isolation` ends with

```python
shared = (gate_imports & scorer_imports) - {"whetstone_gate"}
```

That subtraction **is** an allow-list, it has exactly one entry, that entry is **the package root and
not a pure value type**, and **no ruling exists for it.**

**Why it is not cosmetic.** `_first_party_imports` records the *module* named in a `from X import Y`
statement, so **both** `gates/` and `scorer/` doing `from whetstone_gate import shared_predicate`
record the string `whetstone_gate` — which the subtraction then discards. **Reproduced** (evidence
in `docs/reviews/REVIEW_C0.md` **B-02**): `gates/arm4_kernel.py` and `scorer/replay.py` both importing
and calling one `shared_predicate.intent_key` — hard rule 8's own named spike defect, transliterated —
gives **`PASS D3 no shared first-party module`**.

**Options seen:**
  1. **Delete the subtraction and record shared *names*, not shared module strings** — resolve
     `from whetstone_gate import X` to `whetstone_gate.X` so the two sides can be compared at the
     module they actually share. No allow-list needed for the package root, because the package root
     stops being a value either side can record.
  2. **Keep the subtraction and rule it in**, as an explicit allow-list entry with the reason written
     down. — Cheapest, and **wrong**: it would bless exactly the escape hatch B-02 walks through.
  3. **Build the allow-list hard rule 8 actually describes** — the three named pure value types, by
     module path, asserted to contain no predicate logic — and let everything else fail.

**Default taken pending a ruling:** **none. Nothing was changed.** A review session fixes nothing
(`CLAUDE.md` §1), and this needs a ruling regardless of who writes the code, because hard rule 8
routes allow-list decisions through this file by name.

⚠️ **The allow-list is only one of B-02's three causes.** The other two — `from .. import scorer`
being invisible to D1, and the walk being one level deep where hard rule 8 says **transitive** — are
plain defects and need no ruling, only a fix.

**RULING (architect, 2026-08-31):** *OPTION 1. THE SUBTRACTION IS DELETED. There is no allow-list
entry for the package root and none is created.*

*`from whetstone_gate import X` must be RESOLVED to `whetstone_gate.X` before the two sides are
compared, so that `gates/` and `scorer/` are compared at the module they actually share. The
package root then stops being a value either side can record, and no allow-list entry for it is
needed.*

*OPTION 2 IS REJECTED EXPLICITLY. Ruling the subtraction in as an allow-list entry would bless
exactly the escape hatch `REVIEW_C0.md` B-02 walks through - and under Q-004's ruling the package
root is now the COMMONEST import string in the project, so allow-listing it would make D3
permanently blind. Hard rule 8 permits an allow-list only of "pure value types (enums, the
harm-record dataclass, the paise integer wrapper) that carry no predicate logic". A package root
is not a pure value type.*

*THE ALLOW-LIST HARD RULE 8 ACTUALLY DESCRIBES IS CREATED, AND IT IS CREATED EMPTY. None of the
three named pure value types exists yet - the harm-record dataclass is C4's, the enums and the
paise wrapper are C4's and C8's. It ships as an explicit named constant, empty, carrying a
comment stating that ADDING TO IT IS A CLASS A DEVIATION REQUIRING AN ARCHITECT RULING IN
`QUESTIONS.md`, per hard rule 8, which routes allow-list decisions through that file BY NAME.
C4, C8 and C9 will each ask for entries. EACH ASK IS A SEPARATE RULING, judged on whether that
specific module carries predicate logic. NONE IS EVER GRANTED IN BULK.*

*B-02's OTHER TWO CAUSES NEED NO RULING, ONLY THE FIX, and they are named here so the fix session
cannot close B-02 on the allow-list alone: (a) `head = module.lstrip(".").split(".")[0]` yields
the empty string for `from .. import scorer`, so a relative import crossing the moat is not
recorded at all - relative imports must be resolved against the importing file's own package;
(b) the walk is ONE LEVEL DEEP where hard rule 8 says TRANSITIVE - it collects the direct imports
of files under `gates/` and `scorer/` and never follows them, so the one-hop attack (each side
imports its own helper; both helpers import the shared predicate) passes. The walk must follow
first-party imports transitively.*
