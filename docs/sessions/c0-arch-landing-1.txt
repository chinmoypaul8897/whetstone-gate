## INC-13 - a backspace byte sat inside the spec for two days and was reported as a typo

**Date:** 2026-08-31

**Event:** While landing Q-005's ruling - a one-word path correction - the
editor tool refused three times to match the literal string `MinGWin` that
`grep`, the file viewer and every prior session had displayed in `CONTEXT.md`
section 16. `od -An -tx1` showed why: the byte between `MinGW` and `in` is
`0x08`, a BACKSPACE, not the `\b` of `\bin`. `git show 310488d:CONTEXT.md`
carries it too, so it has been in the specification since v1.0 (`104fc74`), and
`git diff` was empty, so no session in this repository introduced it.

**Action:** Confirmed at byte level in the working tree, in `HEAD`, and at
v1.0. Swept every tracked file for C0 control bytes and established that
`CONTEXT.md` was the only tracked text file carrying one. Repaired it with a
script written to the OS temp scratchpad containing no backslash character
anywhere in its source (the backslash built as `bytes([92])`), which refused to
run unless it found exactly one occurrence and asserted afterwards that the file
grew by exactly one byte and that zero control bytes remained. Recorded the
misdiagnosis in `QUESTIONS.md` context, `PROGRESS.md`, `STATUS.md` and
`CONTEXT.md` v1.2's change-log row without editing the verbatim ruling.

**Expectation:** A repository whose freeze rests on byte-level integrity, and
which runs four dedicated line-ending and object-store checks over every tracked
file, should not be able to carry an invisible control character inside its own
specification for two days - still less have that character read by a build
session, a completion session, a correction session and a full adversarial
review, and be written up by one of them as a spelling mistake.

**Missing:** A check on tracked-document CONTENT. `check-roles` A1-A4 answer
"are the line endings right" and "do the worktree and the object store agree".
Nothing answers "does this document contain a byte that no prose document should
contain". A one-line scan for C0 control bytes other than TAB and LF over every
file git classifies as text would have caught this on the first commit, costs
nothing, and has no false positive in this repository - the sweep run today
returned exactly one hit, and it was the defect.

**Missed:** Two signals, both present and both ignored. (1) `CONTEXT.md`
section 16 gave two different paths for the same executable four lines apart -
Q-005 noticed the discrepancy, measured the filesystem, and correctly concluded
the command was right; it then stopped at "typo" without asking why a typo would
duplicate the neighbouring string so exactly. `C:\MinGWin\` is not a plausible
mistyping of `C:\MinGW\bin\`; it is that string with one character eaten.
(2) `REVIEW_C0.md` re-derived the line-ending property independently, reported
"40 tracked files, 0 mismatches", and read this line while doing it. Both
sessions looked directly at the corrupted bytes and both saw the rendered text
instead.

**Diagnosis:** A backspace does not survive rendering, so every tool that
displays text showed a plausible-looking wrong path rather than a corrupted one;
and every check the repository owns asks about line endings or about
worktree-versus-blob equality, both of which a lone `0x08` satisfies perfectly.
The defect was invisible to the eye and out of scope for the machine.

**Fix:** The byte is removed and section 16 now reads
`C:\MinGW\bin\mingw32-make.exe`, in commit `63da93a` (`CONTEXT.md` v1.2).

**Systemic guardrail:** OWED, NOT YET BUILT, and it belongs to the C0 FIX
session together with OF-01: a new `check_gitattributes` check asserting that
**no tracked file git classifies as text contains any C0 control byte other than
TAB (0x09) and LF (0x0A)**, with a mutation test that fails on the old code.
This is a strict superset of OF-01's proposed lone-CR discriminator - a lone CR
is `0x0D` outside a CRLF pair - so ONE check closes both, and it does not
duplicate git's own text/binary heuristic, so hard rule 8's anti-circularity
objection does not apply to it.
