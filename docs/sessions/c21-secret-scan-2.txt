S8 fixes the method as `git log -p --all | grep -nEi '<key patterns>'`. All 8
branches were driven against constructed positives. SEVEN discriminate correctly
and ONE DOES NOT.

⚠️ GNU grep's ERE HAS NO NON-CAPTURING GROUP. The private-key pattern is
`-----BEGIN (?:RSA |EC |OPENSSH |PGP )?PRIVATE KEY-----`. GNU grep 3.0 discards
the leading `?` inside the group, leaving `:RSA ` as the first LITERAL
alternative. The variant slot is written `<X>` below because writing the real
headers trips check_roles C1 on a tracked file - see section 9.

    -----BEGIN <RSA> PRIVATE KEY-----      grep: NO MATCH     python re: MATCH
    -----BEGIN <EC> PRIVATE KEY-----       grep: match        python re: MATCH
    -----BEGIN <OPENSSH> PRIVATE KEY-----  grep: match        python re: MATCH
    -----BEGIN <PGP> PRIVATE KEY-----      grep: match        python re: MATCH
    -----BEGIN <none> PRIVATE KEY-----     grep: match        python re: MATCH
    -----BEGIN <:RSA> PRIVATE KEY-----     grep: MATCH        python re: no

⚠️ THE PRESCRIBED FORM MISSES THE COMMONEST PRIVATE-KEY HEADER THERE IS, and
matches a string that will never occur instead. A second, smaller divergence:
the prescribed form is case-INSENSITIVE (`-i`) while check_roles C1 calls
`re.finditer` case-SENSITIVELY - the two were never the same scan.

⚠️ THIS CHANGES NOTHING ABOUT THIS RUN'S VERDICT, and saying so matters as much
as raising it: method B uses check_roles' own Python `re`, so the branch is
honoured, and NO PRIVATE-KEY BLOCK OF ANY VARIANT EXISTS ANYWHERE IN THIS
